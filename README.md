# CargoClear — Autonomous Maritime Letter of Credit & Cold-Chain Customs Escrow

A pure GenLayer Intelligent Contract (no frontend, no backend, no hosted service). An importer
locks native GEN against a shipment; an accredited **Carrier Authority** attests the Electronic
Bill of Lading — container **and vessel IMO** — with an **Ed25519 signature verified inside the
contract**; funds then move in two tranches only when **2 of 3 independently keyed witnesses**
(carrier manifest, port customs, cold-chain AIS telemetry) each deliver a **signed** record bound
to that exact shipment and agree on what happened to the container. Settlement is integer basis
points, with cold-chain and demurrage haircuts, and every wei is accounted for.

## What changed from v1

v1 read three static JSON files from **one GitHub repository** through three CDN mirrors
(`raw.githubusercontent.com`, `cdn.jsdelivr.net`, `raw.githack.com`). The hosts differed, the
publisher did not, and nothing in the files was authenticated: whoever could push to that repo
could decide a settlement. That was correctly rejected as "static mock records from one
repository publisher". v2 removes the assumption that *where a record is fetched from* says
anything about whether it is true:

| | v1 | v2 |
|---|---|---|
| Why a record is believed | it was served from a pinned URL | its **Ed25519 signature verifies** against the witness key fixed at deployment |
| Sources | 3 CDN mirrors, 1 repository, 1 publisher | **3 witness slots, 3 distinct keys**, 3 distinct hosts, any HTTPS endpoint |
| Shipment binding | `bol_record_id`, `lc_id`, `container_id` strings | signed **nonce** = `sha256(BoL id ∣ container ∣ vessel IMO)` plus the three identifiers |
| Vessel | not modelled | **IMO** (7 digits, check digit validated), signed by the Carrier Authority into the BoL |
| Quorum | 2 matching records | 2 matching records from **2 distinct witness keys** |
| Unauthenticated record | n/a | an *outage*: it can not vote, can not reject, can not move money |
| Static git mirrors as endpoints | required | **refused by the contract** |

## The honest limit of this repository

The contract can verify who signed something; it can not conjure a real shipping line, port
authority or AIS network. **There are no real maritime or customs providers behind this
repository, and nothing here stands one up.** The three witness keys used in the deployment are
demo keys generated by the operator of this project (`scripts/cargoclear_witness.py`,
`.secrets/`, git-ignored). What v2 delivers is the architecture a real provider plugs into:

* To go live with real providers, each provider generates its own Ed25519 key, publishes records in
  the `cargoclear.evidence.v2` format below at an HTTPS endpoint of its choosing, and the
  deployer passes the **three public keys** to the constructor. No contract change is needed.
* Until then, the deployed contract's witness endpoints are **placeholders on the reserved
  `.example` TLD that can never resolve**. So on Studio Next the live proof below shows the
  contract's *guards and its fail-closed behaviour*; the happy path with authentic signed
  records (3-of-3 Stage 1, 2-of-3 Stage 2 with a dissenting AIS witness, rejections, tamper and
  forgery cases) is proved by the direct-mode test suite, which signs with an independent
  Ed25519 implementation (OpenSSL via `cryptography`). I did not publish simulated records on any
  third-party host just to get a green live settlement.

## Design

* **Zero floats.** Temperatures are integer tenths of °C (`-180` = −18.0 °C), shares are basis
  points, money is wei. Views return only `int/str/bool/list/dict` and the evidence parser rejects
  every float spelling (`1.0`, `1e2`, `-0.0`, `NaN`, `Infinity`) plus duplicate keys,
  booleans-as-ints, extra/missing keys and oversized bodies.
* **In-contract Ed25519 (RFC 8032).** The Carrier Authority key and the three witness keys are fixed
  at deployment. All four must be canonical, non-small-order points **and pairwise distinct**
  (a witness can not also be the Carrier, and one key can not fill two slots).
  `verify_bill_of_lading(lc_id, bol_record_id, sig)` rebuilds
  `bol_record_id|lc_id|container_id|vessel_imo|exporter_address|cargo_spec_hash|max_temp_tenths_c|latest_arrival_ts`
  from the stored L/C terms and verifies it with pure integer arithmetic (Shamir's trick, canonical
  encodings only, `S < L`). A bad signature reverts `ERR_INVALID_BOL_ATTESTATION` before any fetch
  or write. One BoL id can back only one L/C.
* **Signed, shipment-bound evidence (`cargoclear.evidence.v2`).** Each witness returns a flat JSON
  object with exactly these keys: `schema, role, binding, bol_record_id, container_id, vessel_imo,
  status, departure_ts, arrival_ts, event_ts, peak_temp_tenths_c, signature`. The signature is
  Ed25519 over

  ```text
  cargoclear.evidence.v2|role|binding|bol_record_id|container_id|vessel_imo|status|departure_ts|arrival_ts|event_ts|peak_temp_tenths_c
  ```

  and `binding = sha256("cargoclear.binding.v2|" + bol_record_id|container_id|vessel_imo)` is the
  shipment nonce. A record counts only if **all** hold: well-formed; `role` equals the slot's role;
  `bol_record_id`, `container_id`, `vessel_imo` and `binding` equal the L/C's verified BoL, container
  and IMO; the signature verifies against **that slot's** key. Each signed field is covered (tamper with
  the temperature, status or any timestamp after signing and verification fails). Replaying one L/C's
  evidence on another fails because a BoL id binds to a single L/C. Anyone can ask the deployed
  contract whether a record would authenticate: `check_evidence(lc_id, slot, record_json)`.
* **Endpoints.** The importer supplies three HTTPS URLs when opening the L/C: DNS hostnames only
  (no IP literal, port, userinfo, query, fragment, percent-encoding or traversal), **pairwise
  distinct hosts**, and none on a static git-hosting mirror (`githubusercontent.com`,
  `jsdelivr.net`, `githack.com`, `github.io`, `gitlab.io`). Host choice does **not** decide trust —
  signatures do — it only gives three separate transport paths, so one outage or one censoring host
  can not silence the quorum. Exporters should still inspect `get_evidence_sources` during the
  handshake: it prints each slot's role, URL and the Ed25519 key that slot is verified against.
* **48-hour bilateral handshake.** `open_letter_of_credit` → `PENDING_EXPORTER_ACCEPTANCE`. The
  named exporter may `accept_lc_terms` / `reject_lc_terms` (the deadline itself is still inside
  the window). If rejected, or still unaccepted after 48 h, the importer calls
  `cancel_unaccepted_lc` and reclaims 100 % of principal.
* **Two tranches.**
  * `STAGE_1_DEPARTURE` — 2000 BPS (20 %): ≥ 2 distinct witnesses confirm departure for the same
    shipment with `0 < departure_ts <= latest_arrival_ts`.
  * `STAGE_2_CUSTOMS_CLEARED` — 8000 BPS (80 %), by bucket (shares of the whole L/C):

    | bucket | condition | exporter | importer |
    |---|---|---|---|
    | 0 `CLEAN_DELIVERY` | `peak <= max`, `arrival <= latest` | 8000 | 0 |
    | 1 `LATE_DEMURRAGE` | clean temp, `latest < arrival <= latest + 7 d` | 6000 | 2000 |
    | 2 `MINOR_THERMAL_DRIFT` | `max < peak <= max + 30` | 4000 | 4000 |
    | 3 `SPOILED_OR_REJECTED` | `peak > max + 30`, or arrival > 7 d late, or customs rejected | 0 | 8000 |

    Lateness and drift combine to the **worse** bucket. Rounding dust (the sum of floors) goes to
    the exporter on bucket 0 and to the importer on every haircut bucket, so
    `exporter_claimable + importer_rebate + unreleased + withdrawn == total_deposited` always.
* **Independent corroboration in `aggregate`.** Consensus payload is exactly
  `{"verdict","stage","bucket","source_count","evidence_digest","event_ts"}`. `verdict 1` = ≥ 2
  **distinct witness keys** agree on `(stage, bucket)` for this shipment's binding; `verdict 0` = ≥ 2
  distinct witnesses attest `CUSTOMS_REJECTED` / `VOYAGE_ABORTED` (Stage 2 → bucket 3; a corroborated
  abort before Stage 1 refunds everything still in escrow); everything else — fewer than 2
  authenticated responders, `1 CONFIRMED + 2× 404`, `1 CONFIRMED + 404 + OUTAGE`, conflicting
  positives, **unsigned or wrongly-signed records**, future timestamps (`> now + 3600`) — is
  `verdict 2 QUORUM_FAILURE`: **retryable and it mutates nothing** except a diagnostic counter. A
  404, an outage or a forgery can never produce a rejection. `evidence_digest` is
  `sha256("cargoclear.corroboration.v2|binding|stage|bucket|POS-or-REJ")`, which ties the agreed
  outcome to the shipment. Validators re-fetch, re-authenticate and require exact equality of all
  six fields (exact key set, int/str types).
* **Liveness.** `reclaim_expired_lc`: if nobody settles within `latest_arrival + 7 d + 30 d`,
  the importer recovers whatever is still in escrow.
* **Payouts** are pull-pattern (`claim_funds`), checks-effects-interactions, restored if the
  transfer cannot be enqueued. No owner, no pause, no upgrade, no fee.

Beyond the spec: Stage 2 requires Stage 1; settlement requires a verified BoL; only L/C parties
may trigger settlement; the clock is `gl.message.raw["datetime"]` (the transaction time),
captured outside the non-deterministic block.

## Trust Model, Demo Scope & Known Limitations

**Trust model.** Funds move only on (a) a valid Ed25519 attestation by the Carrier Authority key
fixed at deployment and (b) signed, shipment-bound records from at least two of three distinct
witness keys. Anyone who controls the Carrier key can attest any Bill of Lading, and any two
colluding (or compromised) witness keys can decide a bucket for a shipment the Carrier has
attested. CargoClear minimises trust; it does not remove it. Its security is exactly the
independence of the four key holders in a given deployment — which is a fact about the world,
not something a contract can establish.

* **Demo keys in this deployment.** The Carrier Authority key and the three witness keys of the
  Studio Next deployment are demo keys held by one operator, and its witness endpoints are
  unresolvable placeholders. This is a rehearsal of the architecture, not independent oracle
  coverage. A production deployment needs a real accredited authority key and three witnesses run
  by genuinely separate organisations, each with its own key and its own endpoint.
* **Immutable authorities.** All four public keys are set in the constructor; there is no setter,
  rotation or admin path. Replacing or revoking a key means deploying a new contract; open letters
  of credit on the old contract keep their original keys.
* **No freshness beyond `event_ts`.** A genuine, correctly signed `CUSTOMS_CLEARED` record for a
  shipment stays valid for that shipment (it is bound to one BoL, so it can not be replayed on
  another). The contract bounds timestamps to `now + 1 h`; it does not expire old events.
* **Post-grace exporter reclaim risk.** If the witnesses stay unreachable (or never reach quorum),
  nothing is settled and the importer may call `reclaim_expired_lc` once
  `latest_arrival_ts + 7 days (grace) + 30 days (settlement window)` — 37 days after the
  contractual arrival time — has passed. It returns everything still in escrow to the importer, so
  an exporter whose cargo arrived but whose witnesses are down for that long loses the unsettled
  tranches. Funds already released by Stage 1 stay with the exporter. **On the Studio Next
  deployment the L/C stays in escrow for exactly this reason** (placeholder endpoints).
* **Importer endpoint selection.** The importer chooses the three URLs. Because records are
  signed, a malicious URL can only withhold evidence (a liveness problem), never forge it —
  but **exporters must read `get_evidence_sources` during the 48-hour acceptance handshake** and
  reject an L/C whose endpoints they do not recognise as the registered witnesses' own.
* **Distinct hostnames are not distinct operators.** The contract enforces distinct hosts and
  refuses known git mirrors; it can not know that two hostnames belong to one company. Operator
  independence is carried by the keys.
* **Read cost.** `get_protocol_summary` is O(1) (counters updated on every transition).
  `verify_solvency_invariant` is deliberately an independent from-scratch audit and scales
  **linearly** with the number of L/Cs; call it sparingly on a protocol with very many letters.
* **Malformed fetches are outages.** `fetch_source` reads status/body defensively: anything
  unexpected is an `OUTAGE` that cannot vote, so an RPC outlier yields a retryable
  `QUORUM_FAILURE` instead of reverting the transaction.

### Payouts on Studio Next (observed in v1, not a contract fault)

`claim_funds` debits the ledger and emits the payout with `emit_transfer(..., on="finalized")`.
In the v1 live run the emitted message (correct recipient and amount) was recorded in each tx's
`messages`, but **Studio Next did not credit the recipient EOA in the ~10 minutes observed**; a
minimal test contract using `emit_transfer` behaved the same way. The accounting and the emitted
messages are verified; actual EOA crediting is something that Studio deployment did not perform.
The v2 live run does not reach a claim (nothing settles without authentic witnesses), so this is
covered by the v1 record and the direct-mode tests.

### What the tests cover

* **`test_evidence_auth.py`** — the evidence authentication model. Authentic records from three
  keys settle (3-of-3 Stage 1; 2-of-3 Stage 2 with a dissenting AIS witness); unsigned legacy
  records, records from an unregistered key, from the Carrier Authority key, from another slot's
  witness, with the wrong role, with a garbage / short / uppercase / malleable (`S ≥ L`) signature,
  tampered after signing in each signed field, registered witnesses lying about the BoL / container
  / IMO / nonce, another ship's perfectly consistent evidence, and one compromised key filling all
  three slots are each refused with no state change, are retryable, and can not reach a
  rejection or a refund; plus the `check_evidence` view and an independent IMO check-digit oracle.
* **`test_aggregate_quorum.py`** — all **343** per-source behaviours (positive×2, rejection, 404,
  outage, future-dated, unauthenticated) × 2 stages against an independent oracle, on the pure
  aggregate **and** end-to-end through the contract; "two records from one key are one voice";
  bindings to different shipments never join a quorum; 37 malformed or unauthentic bodies; float
  smuggling; the future-timestamp boundary; validator key-set / type / equality.
* **`test_ed25519_bol.py`** — RFC 8032 vectors; 60 random keys/messages cross-checked against
  OpenSSL; every signature byte flipped; malleable `S ≥ L`; non-canonical and off-curve points;
  constructor refusal of bad carrier/witness keys, duplicate keys and a witness equal to the
  Carrier; the forged-BoL path; all **eight** BoL message fields (incl. IMO) individually altered.
* **`test_settlement_math.py`** — every bucket boundary (±1 tenth, ±1 second, the 7-day grace);
  exact BPS; conservation for 60+ principals × 4 buckets; dust direction; payouts drain exactly
  what is owed; AST proof of no floats / no `/` / no `float`; views survive calldata round-trip.
* **`test_contract_flows.py`** — full lifecycle, 48 h boundaries, IMO validation, 30+ endpoint
  rule attacks (schemes, ports, IP literals, userinfo, traversal, git mirrors, shared hosts),
  authorization, replay, expiry, double claims, failed-transfer rollback, and **70 mutants**
  (changed constants, flipped comparisons, removed signature / binding / role / IMO checks, a
  non-distinct-signer quorum, …) that the suite must kill; all 70 are killed.

Test-environment note: GenVM's direct-mode harness does not re-inject the transaction datetime
after load, so tests move the clock by updating both the VM and `genlayer.message.raw["datetime"]`.
